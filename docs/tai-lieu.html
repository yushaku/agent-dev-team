Tài liệu

Chính sách này trả lời: tài liệu nào được commit, ai sở hữu, và cái gì chỉ là scratch. Markdown và JSON là nguồn cho agent. HTML là bản cho người đọc, sinh ra từ nguồn và không thêm sự kiện nào nguồn không có.

Tài liệu ngoài danh sách là tham chiếu chỉ đọc cho tới khi PO chuyển hoặc xóa (docs.legacy). API reference và schema doc: sinh từ code khi cần, không lưu.

Hai nhóm người đọc

  • Agent đọc nguồn (markdown, JSON). Người đọc HTML. Không sửa tay HTML: sửa nguồn rồi render lại.
  • Sơ đồ giữ lại trong docs/diagrams/: tổng quan hệ thống (C4 container view) luôn có; sơ đồ deploy khi hạ tầng có hơn một runtime. Sơ đồ khác vẽ theo yêu cầu trong PR hoặc thảo luận và không lưu, trừ khi PO muốn giữ.

Business spec

  • Một file cho mỗi capability. Viết bằng tiếng Anh, chỉ dùng ngôn ngữ nghiệp vụ: không nêu giải pháp, công nghệ, tên màn hình, API, database, code hay đường dẫn.
  • Gồm: Purpose, Actors, user story đánh số (US1...), quy tắc đánh số (R1...), flow chính và ngoại lệ, acceptance criteria Given/When/Then (AC1...), Glossary, Out of scope, Open questions (rỗng trước Gate 1) và dòng cuối Retired: ....
  • Cỡ: khoảng 80 dòng, quá 150 dòng thì tách capability.
  • ID không bao giờ dùng lại hay đánh số lại. Test tham chiếu spec bằng tên file capability, ví dụ garden AC3: ...; spec không tham chiếu test hay code.
  • Câu trả lời Gate 1 và quyết định của PO ghi trong .team/<feature>/decisions.md, Tech Lead gộp thành quy tắc và AC. Lịch sử nằm ở git log của spec.

Scratch: .team/ (không commit)

  • .team/<feature>/: plan.md, decisions.md, walkthrough.html (Gate 1 cho PO), handoff.md, design/, specs/ và báo cáo role dạng <role>-r<N>.md.
  • .team/research/<topic>.md: kết quả phiên Researcher, dưới 60 dòng.
  • .team/carry-over.md: các mục Should fix còn lại sau merge, mỗi mục một dòng.
  • Chỉ .team/config.yaml được phép commit. Đóng Run thì xóa .team/<feature>/, giữ carry-over.md và research/.

Quy tắc khác

  • Site xuất bản: tùy chọn theo repo (docs.site: pages, mặc định off). Repo công khai thì mọi tài liệu commit đều lộ: không để bí mật, dữ liệu cá nhân, tên client hay điều khoản chưa phát hành trong docs/. Bật Pages là bước của PO.
  • Xung đột: ADR hoặc README mâu thuẫn với code thì code thắng. Business spec mâu thuẫn với code thì Tech Lead quyết bên nào sai; đổi quy tắc nghiệp vụ là quyết định của PO (Gate 1).
  • Viết: mỗi câu phải mang một sự kiện, quy tắc hay quyết định mà người đọc không lấy được từ code, config hay tài liệu khác. Xóa câu mà bỏ đi không ai làm khác đi.
  • Audit tài liệu: là việc S0, ra bảng từng tài liệu (giữ, chuyển, legacy, xóa), rồi đề xuất một Run dọn S1. Không đổi gì trước khi PO đồng ý.
