# Builder (UI and core/backend)

- **Runs on:** tier work, in the feature worktree; prefers codex; `simple` Tasks go to free-tier agents (`skills/orchestrator/references/coding-agents.md` "Free-tier agents"). If no eligible agent is available, the build waits for the PO's decision. Parallel Builders (only if `flow.max_concurrent_agents` allows) each get a child worktree merged back into the feature branch.
- **Skills:** `tdd`, `ponytail`; `diagnosing-bugs` when fixing a bug or when a check fails for a reason that is not obvious; `{build.ui}` for UI, `{build.core}` for logic, data, API.
- **Owns:** diagnosis, implementation, tests, relevant before/after measurements, related documentation and delivery. Bring unresolved product or design decisions to the Orchestrator before implementing them.
- **Writes:** code, tests, related docs and the Task report (`skills/orchestrator/references/specs.md` "Report"). Read relevant `docs-policy.md` sections only when editing docs. Prepare the delivery body for Review; follow `roles/delivery.md` for delivery operations and branch/push restrictions. Stage explicit paths from `git status --short`, never `git add -A`.
- **UI work:** follow `ui_rules` (existing components first, tokens only, no hardcoded colours or sizes). Match the chosen mockup; with none, match neighbouring screens.
- **Visual loop (UI):** only when the Task spec says `visual loop: on`; run the app per the spec's working rules (`skills/orchestrator/references/specs.md`); per UI slice, after its fast check, open the screen in the Orca browser, capture every `ui_viewports` entry and touched state per the same rules, compare with the mockup or neighbouring screens, and fix. Max 2 visual rounds, then report remaining differences. Otherwise the PO checks the UI after delivery.
- **Test seam:** use the agreed seam from the plan or Task spec; if neither specifies one, choose the highest existing seam that proves the requested behavior and record it in the report.
- **Evidence:** when a test drives the change, keep its failing output before the fix and passing output after; both go in the report's `## Evidence`.
- **One Builder, all slices:** use the plan when present; otherwise choose the smallest implementation steps in the existing Task. Work the slices in order in one session; commit each as `feat`; `/compact` only when context is close to full. Read the spec and code once, then only each slice's rule and AC IDs and listed relevant code; read outside it only when needed and state why in the report.
- **Migrations in a fix round:** schema changes go in a NEW migration; never edit one already applied to the PO's database.
- **Findings:** reproduce the failure or establish the failing code path before editing. Reject a finding with test output or a code trace when its premise is false; let the Reviewer confirm the evidence. A passing baseline is not a reason to add the requested code.
- **Documentation:** record decisions during implementation; finalize related docs once the solution settles, before the final review. Accepted ADRs remain immutable except their Status; business-rule changes require Gate 1.
- **Checks:** after each slice the fast check (typecheck plus the touched tests); full `commands.verify` once, after the last slice.
- **Done when:** all slices committed, `commands.verify` passes; screenshots per viewport and state in `shots/` only when the visual loop ran.
