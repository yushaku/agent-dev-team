Ledger: system design

Draft Updated 6 Nov 2026

Overview

Ledger is an offline-first expense tracker. A PWA stores entries locally and syncs them through one Cloudflare Worker to D1; receipt photos go to R2 and are read by an async OCR job.

Architecture

Quality goals

Offline first

Every write lands in IndexedDB first. The app stays usable with no network for days.

Cheap to run

Stays inside the Workers paid plan base fee up to 10,000 monthly users.

Private by default

Receipts are never public. R2 objects are read only through the Worker.

Flows

Two flows carry most of the load: syncing local entries and reading a receipt. Both tolerate retries because every write carries a client-generated id.

Sync local entries

  1. PWA saves the entry to IndexedDB with a ULID and marks it pending.
  2. Service worker batches pending entries when the network returns, up to 100 per request.
  3. API Worker validates the batch and upserts rows in one D1 transaction.
  4. API Worker returns the server cursor; the PWA clears pending flags up to it.

Read a receipt

  1. PWA uploads the photo with PUT /api/receipts/:id.
  2. API Worker stores it in R2 and enqueues { id, key } on ocr-jobs.
  3. OCR consumer reads the image, calls the vendor API and writes the total to D1.
  4. PWA picks up the parsed total on its next sync.

NoteFailed jobs retry three times with backoff, then land in ocr-jobs-dlq for manual review.

Decisions

Accepted decisions are binding until superseded. Proposed ones need a review before the next release.

ADR-001

Use D1 instead of a hosted Postgres

Accepted
Context
Data is small, per user, and read near the user. A Postgres connection from Workers adds latency and a second vendor.
Decision
Store all relational data in D1 with read replicas enabled.
Consequences
No cross-user analytics in the primary store; nightly export to R2 covers reporting.
ADR-002

Run OCR asynchronously through a queue

Accepted
Context
The vendor API takes 2 to 6 seconds, longer than a good upload response.
Decision
Upload returns at once; a queue consumer does the OCR.
Consequences
The total appears on the next sync, not instantly.
ADR-003

Sign in with passkeys only

Proposed
Context
Email codes cost money and land in spam for some providers.
Decision
Use WebAuthn passkeys, with a recovery code shown once.
Consequences
Users on old Android builds need a fallback; to be decided.

Decision neededPick the passkey fallback by 20 Nov 2026: email code or device link. Owner: Platform lead.
