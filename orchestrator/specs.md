# Task specs

- Write each spec to `<main checkout>/.team/<feature>/specs/<NN>-<role>.md` as an absolute path; it is git-ignored and survives the session. Pass `--spec-file <file>` and run one `task-create` per command. Get the id from `result.taskId` or `result.task.id`, otherwise use `task-list --run <id> --json`.
- Set the title with `--task-title "<role>: <what>"`, using the role id in `config.md` `models.roles` (for example `builder: slice 1 checkout`, `reviewer: re-review round 1`). Start the spec with `Role: <role>`; usage is reported per role from these specs.
- Make each spec self-contained and include the role card with slots resolved.
- Put skills immediately after `Role:` as absolute `SKILL.md` paths under the skills dir: `First step, before reading code: read ~/.agents/skills/<a>/SKILL.md, ~/.agents/skills/<b>/SKILL.md.` Claude skips bare skill names. Put conditional skills on the next line as `Read ~/.agents/skills/<c>/SKILL.md when <condition from the role card>.` Give skills that exist only in the orchestrating agent's own skills dir as absolute paths.
- Include `commands.verify` (plus "one at a time" when `serial`), `branches.naming`, `human_only`, UI `ui_rules` and `ui_viewports`, and the Tech Lead's `compliance` constraints for Builders.
- For UI roles, say `visual loop: on` only when the PO asked or `ui_rules.visual_loop: on`.
- Put the PO's inputs (reference docs, screenshots, sketches) in `.team/<run>/`, shared with the worktree through the `config.md` link; name the exact section or variant. For sketches, specify the chosen variant and pieces from others as a layout contract, not the mock's colours.
- State the target, change, constraints, allowed files and observable acceptance criteria.
- **Model:** name the tier, model and effort per `coding-agents.md` "Model tiers"; record the effort step and reason if moved. Tasks the Tech Lead marked `simple` (`roles/tech-lead.md` "Simple Tasks") carry the mark and route per `coding-agents.md` "Free-tier agents". Reviewer tier is never below the Builder's for the same task. Multi-behaviour fix rounds and migration edits stay at tier work.
- Include the pre-cut rule and AC IDs for the Task, not the whole spec, plus **Relevant code** files and symbols from the plan or one read-only explorer worker. Workers read `AGENTS.md` and the listed code, never the whole `docs/`. Get IDs from the final spec with `grep "^- AC"`; IDs can have gaps. Do not copy IDs from a PM message (`docs-policy.md`, Business spec).
- **Working rules** for every Builder: allow reading any file, editing only Task files, focused tests, a dev server per `orca.md` "Dev server and app processes", screenshots, and git status/diff/log/add/commit on the branch. With network forbidden, official docs pages are still allowed. Ask the Orchestrator with the exact command only for remote ops, push, deploy, other roles' files or an unplanned dependency. Include broken verify commands and the prior Task handoff. Never write "ask for everything else"; Codex stops before reading files.
- Include the PO's uncommitted files as read-only in every Task spec; workers must not edit, stage or delete them.
- Exception: Codex in a worktree of the main checkout cannot `git add`; ask it not to commit and to report changed paths. The Orchestrator reruns verify and commits those explicit paths before the next Task. Codex Delivery specs are edit-only, with no commits.
- Conversation UI features (attachments, reactions, edits): the spec states how the sent message shows after a reload; the service that owns the history stores it, client memory is only a fallback that switches off once the field exists.
- Record a deferred capability and open questions as a numbered item in `.team/<feature>/decisions.md`; keep v1 behaviour unchanged.
- Link the numbered item in `.team/<feature>/decisions.md` in every later Builder spec when a PO decision came after the plan was written.
- Reject a plan with more than 4 slices, or split it by layer, unless it states a reason.
- Use one simple command per Bash call. Avoid shell variables (`F=...; $F`) and semicolon chains with the heartbeat; compound commands miss the allowlist and stall workers on a prompt.
- Create no new `.md` files except role outputs. Do not create backup copies such as `*.bak` or `*.v1.md`; put results in `worker_done`.
- Run `git status --short` and stage explicit paths, never `git add -A`.
- Delivery specs that delete or rewrite files include a keep-list of files the PO chose to keep. Before Delivery commits, compare `git status --short` deletions with it, restore unapproved deletions and report them at Gate 2.
- For maintenance, read `branches.client_visible`; require a failing reproduction test first, named with the ticket key.
- When PM and Tech Lead start in parallel, list every divergence before the Builder spec. Ask the PO about user-visible divergences one question at a time; decide technical divergences yourself.
- The Builder spec says the spec wins on user-visible behaviour, includes the override list, and asks a PM tidy Task to align the spec. Before slice 1, the Builder diffs plan against spec and sends remaining conflicts in one question.
